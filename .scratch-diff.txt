+# Forecasting Scheduler & Worker Operations
+
+This document provides operational instructions for deploying and maintaining the scheduled ML worker, which is responsible for daily Forecast Generation and weekly Model Retraining.
+
+## Supported Deployment Topologies
+
+The scheduled worker requires reliable execution and must not be interrupted by desktop power savings or employee workstation restarts.
+
+**Supported:**
+* **Dedicated Windows Store-PC:** Must be configured to prevent sleep/hibernate during off-hours. Power-loss recovery (BIOS auto-power on) and a UPS are strongly recommended.
+* **Linux VPS (Virtual Private Server):** Ideal for reliable cron-based execution.
+
+**Unsupported:**
+* Shared hosting environments lacking persistent Python virtual environments or cron access.
+* Ordinary employee workstations that are regularly powered off or put to sleep after the store closes.
+
+## Windows Store-PC Scheduling (Task Scheduler)
+
+1. Open **Task Scheduler** (`taskschd.msc`).
+2. Click **Create Task...** (not Basic Task).
+3. **General Tab:**
+   - Name: `RetailMind ML Scheduler`
+   - Security options: Select **Run whether user is logged on or not** and check **Run with highest privileges**.
+4. **Triggers Tab:**
+   - New Trigger -> Begin the task: **On a schedule** -> **Daily**
+   - Set the time to after Store close (e.g., `11:00 PM`) and recur every `1` days.
+   - Also, add a trigger to run the worker process loop every 5 minutes if you prefer the PHP scheduler to trigger tasks dynamically.
+5. **Actions Tab:**
+   - Action: **Start a program**
+   - Program/script: `php.exe`
+   - Add arguments: `-f C:\path\to\retailmind\src\backend\scripts\run_scheduler.php`
+6. **Conditions Tab:**
+   - Uncheck "Start the task only if the computer is on AC power" if running on a dedicated PC with UPS.
+   - Check "Wake the computer to run this task".
+7. **Settings Tab:**
+   - Check "Run task as soon as possible after a scheduled start is missed".
+
+### Dedicated PC Power/Security Obligations
+- **Sleep Settings:** Disable automatic sleep in Windows Power Options. The screen can turn off, but the PC must remain awake.
+- **Physical Security:** The dedicated PC should be secured in the back office.
+- **Updates:** Configure Windows Updates to run outside of the schedule windows to avoid unexpected restarts during ML training.
+
+## Linux VPS Scheduling (Cron & Virtual Environment)
+
+On a Linux server, the scheduler relies on cron and the Python virtual environment.
+
+1. **Activate Virtual Environment and Install Dependencies:**
+   ```bash
+   cd /path/to/retailmind
+   python3 -m venv venv
+   source venv/bin/activate
+   pip install -r src/backend/scripts/requirements.txt
+   ```
+2. **Configure Cron:**
+   Open crontab with `crontab -e` and add the following entry to trigger the PHP scheduler script every 5 minutes, which delegates to the ML worker if tasks are due:
+   ```cron
+   */5 * * * * cd /path/to/retailmind && php src/backend/scripts/run_scheduler.php >> /path/to/retailmind/storage/logs/scheduler.log 2>&1
+   ```
+   *Note: Ensure PHP and Python are accessible in the cron environment's PATH.*
+
+## Backup & Restore of Metadata and Artifacts
+
+- **Artifacts:** The trained models are stored in `src/backend/storage/ml_models/`. These `*.joblib` files are portable and backward-compatible with the same scikit-learn version.
+- **Metadata:** Training metadata, job statuses, and evaluation metrics are safely stored in the `ml_jobs` and `model_training_runs` database tables. These are included in standard RetailMind SQL backups.
+- **Restore:** Simply copy the `ml_models` folder to the new host and restore the SQL database. The worker will cleanly resume from the last known state.
+
+## Security & HTTPS
+
+- Over-the-network communication between the worker and the database (if hosted separately) must enforce SSL/TLS.
+- The Python ML worker connects directly to the local database securely via environment variable injection (`.env`), eliminating exposed endpoints.
+
+## Monitoring and Recovery
+
+System health surfaces in the Admin Dashboard automatically track:
+- Worker heartbeats and last activity.
+- Missed runs (if no task has completed within 48 hours).
+- Failures and safe diagnostic statuses.
+
+If a run is missed, the scheduler's idempotency guarantees that overlapping processes or lease recoveries will safely catch up without producing duplicate forecasts or promoting duplicate models. Full technical traces of failures are retained in `activity_log` and `model_training_runs`.

+# Kaggle Capstone Dataset
+
+## Source/Provenance
+Dataset: "Store Item Demand Forecasting Challenge"
+URL: https://www.kaggle.com/c/demand-forecasting-kernels-only/data
+Description: This dataset contains 5 years of daily store-item sales data.
+We use Store 1 data to meet the requirement of one Store, at least two full years of daily history, and at least 20 products (up to 50).
+
+## Import Procedure
+The data is provided as a CSV with columns: `date, store, item, sales`.
+The import script filters for `store = 1`.
+We map `item` to internal product ID.
+
+## Product/Category Mapping
+Items 1-50 mapped sequentially to product IDs in the demo database. Categories are generically assigned.
+
+## Date Coverage
+5 years: 2013-01-01 to 2017-12-31.
+
+## Missing Evidence & Transformation Assumptions
+- No stock, calendar, or schedule evidence is available in this dataset. We do NOT fabricate these as observed truth.
+- Data is imported into an explicitly isolated demo database.

+    {

+        $results = [];
+        $calendar = new StoreCalendar();
+        
+        while ($current <= $end) {
+            $dateStr = $current->format('Y-m-d');
+            $startOfDay = $dateStr . ' 00:00:00';
+            $endOfDay = $dateStr . ' 23:59:59';
+            $effectiveEnd = min($endOfDay, $cutoff);
+

+            // Since StoreCalendar uses the requested cutoff time for its historical reproduction:
+            $calStatus = $calendar->getCalendarDateStatusAtCutoff($pdo, $branchId, $dateStr, $cutoff);

+            $stockStmt = $pdo->prepare("
+                SELECT COALESCE(SUM(change_qty), 0)

+            // Sold items

+                  AND s.sale_date >= ? AND s.sale_date <= ?
+            ");
+            $soldStmt->execute([$productId, $startOfDay, $effectiveEnd]);

+            
+            // Reversed items (approved before cutoff)
+            $reversedStmt = $pdo->prepare("

+                FROM sale_reversal_items sri
+                JOIN sale_reversals sr ON sri.reversal_id = sr.reversal_id
+                JOIN sale_items si ON sri.sale_item_id = si.sale_item_id
+                JOIN sales s ON si.sale_id = s.sale_id
+                WHERE sri.product_id = ?
+                  AND s.sale_date >= ? AND s.sale_date <= ?
+                  AND sr.status = 'approved'
+                  AND sr.approved_at <= ?
+            ");

+            $reversed = (int)$reversedStmt->fetchColumn();
+            
+            // Refunded items (created before cutoff)
+            $refundedStmt = $pdo->prepare("
+                SELECT COALESCE(SUM(cri.quantity), 0)

+                JOIN cash_refunds cr ON cri.refund_id = cr.refund_id
+                JOIN sale_items si ON cri.sale_item_id = si.sale_item_id
+                JOIN sales s ON si.sale_id = s.sale_id

+namespace App\Forecasting;

+use PDO;

+use InvalidArgumentException;

+class ModelPromotionService
+{
+    private PDO $pdo;
+    private CandidateEvaluationService $evaluationService;
+
+    public function __construct(PDO $pdo, CandidateEvaluationService $evaluationService)
+    {
+        $this->pdo = $pdo;
+        $this->evaluationService = $evaluationService;
+    }
+
+    public function promote(string $modelVersion, int $superAdminId): void
+    {
+        $evaluations = $this->evaluationService->getEvaluationsByModelVersion($modelVersion);
+        if (count($evaluations) < 3) { // Expecting 7, 14, 28
+            throw new InvalidArgumentException("Incomplete candidate: missing chronological evaluations for $modelVersion");
+        }
+
+        foreach ($evaluations as $eval) {
+            if ($eval['candidate_gate_outcome'] !== 'passed') {
+                throw new InvalidArgumentException("Candidate $modelVersion failed evaluation gate at horizon " . $eval['horizon_days']);
+            }
+        }
+
+        $this->pdo->beginTransaction();
+        try {
+            $stmt = $this->pdo->query("SELECT setting_value FROM platform_settings WHERE setting_key = 'ml_approved_model_version'");
+            $current = $stmt->fetchColumn();
+
+            if ($current === $modelVersion) {
+                // Retry/concurrent request handling - duplicate promotion
+                $this->pdo->commit();
+                return;
+            }
+
+            // Save previous
+            if ($current !== false && $current !== '') {
+                $this->setSetting('ml_previous_approved_model_version', (string)$current, $superAdminId);
+            }
+
+            // Promote new
+            $this->setSetting('ml_approved_model_version', $modelVersion, $superAdminId);
+
+            log_activity($this->pdo, $superAdminId, 'Promote Forecasting Model', 'Platform Settings', null, $current ?: null, $modelVersion);
+
+            $this->pdo->commit();
+        } catch (\Throwable $e) {
+            $this->pdo->rollBack();
+            throw $e;
+        }
+    }
+
+    public function rollback(int $superAdminId): void
+    {
+        $this->pdo->beginTransaction();
+        try {
+            $stmt = $this->pdo->query("SELECT setting_value FROM platform_settings WHERE setting_key = 'ml_previous_approved_model_version'");
+            $previous = $stmt->fetchColumn();
+
+            if (!$previous) {
+                throw new RuntimeException("No compatible previous approved artifact found for rollback");
+            }
+
+            $stmtCurrent = $this->pdo->query("SELECT setting_value FROM platform_settings WHERE setting_key = 'ml_approved_model_version'");
+            $current = $stmtCurrent->fetchColumn();
+
+            // Set current to previous
+            $this->setSetting('ml_approved_model_version', (string)$previous, $superAdminId);
+            // Clear previous
+            $this->setSetting('ml_previous_approved_model_version', '', $superAdminId);
+

+    {
+        $stmt = $pdo->prepare(
+            'INSERT INTO store_calendar (branch_id, calendar_date, status, recorded_by, recorded_at) VALUES (?, ?, ?, ?, CURRENT_TIMESTAMP)'
+        );
+        $stmt->execute([$branchId, $date, $status, $userId]);

+     * Reconstructs the status of a specific date as it was known at the cutoff time.
+     * Returns 'open', 'closed', 'holiday', 'exceptional-closure', or null if unrecorded.
+     */
+    public function getCalendarDateStatusAtCutoff(PDO $pdo, int $branchId, string $date, string $cutoffTimestamp): ?string
+    {
+        $stmt = $pdo->prepare(
+            'SELECT status FROM store_calendar WHERE branch_id = ? AND calendar_date = ? AND recorded_at <= ? ORDER BY recorded_at DESC LIMIT 1'
+        );
+        $stmt->execute([$branchId, $date, $cutoffTimestamp]);
+        $status = $stmt->fetchColumn();
+        return $status === false ? null : (string)$status;
+    }
+
+    /**
+     * Returns an associative array of [date => status] for a range of dates, 
+     * as known at the cutoff time. Missing dates will not be in the array.
+     */
+    public function getCalendarDateRangeAtCutoff(PDO $pdo, int $branchId, string $startDate, string $endDate, string $cutoffTimestamp): array
+    {
+        // To get the latest status per date before cutoff, we can use a subquery or a JOIN.
+        // A simple correlated subquery works well since the range is usually small (e.g., a month).
+        $sql = '
+            SELECT c1.calendar_date, c1.status 
+            FROM store_calendar c1
+            WHERE c1.branch_id = ? 
+              AND c1.calendar_date >= ? 
+              AND c1.calendar_date <= ?
+              AND c1.recorded_at <= ?
+              AND c1.recorded_at = (
+                  SELECT MAX(c2.recorded_at) 
+                  FROM store_calendar c2 
+                  WHERE c2.branch_id = c1.branch_id 
+                    AND c2.calendar_date = c1.calendar_date 
+                    AND c2.recorded_at <= ?
+              )
+        ';
+        $stmt = $pdo->prepare($sql);
+        $stmt->execute([$branchId, $startDate, $endDate, $cutoffTimestamp, $cutoffTimestamp]);
+        
+        $result = [];
+        while ($row = $stmt->fetch(PDO::FETCH_ASSOC)) {
+            $result[$row['calendar_date']] = $row['status'];
+        }
+        return $result;
+    }

+import numpy as np
+import pandas as pd
+from typing import List, Tuple
+
+def rolling_origin_split(df: pd.DataFrame, date_col: str, horizon_days: int, n_splits: int = 3) -> List[Tuple[pd.DataFrame, pd.DataFrame]]:
+    """
+    Creates rolling-origin chronological splits.
+    df must have date_col.
+    Returns list of (train_df, test_df)
+    """
+    df = df.sort_values(by=date_col)
+    dates = df[date_col].drop_duplicates().sort_values().tolist()
+    
+    splits = []
+    
+    # Evaluate the last n_splits periods of length horizon_days
+    # For example, if horizon_days=7 and n_splits=3, we need 21 days at the end for testing
+    
+    for i in range(n_splits):
+        # The test period is [end - (i+1)*horizon_days, end - i*horizon_days)
+        test_end_idx = len(dates) - i * horizon_days
+        test_start_idx = test_end_idx - horizon_days
+        
+        if test_start_idx < 1:
+            break # Not enough data
+            
+        test_start_date = dates[test_start_idx]
+        if test_end_idx < len(dates):
+            test_end_date = dates[test_end_idx]
+            test_mask = (df[date_col] >= test_start_date) & (df[date_col] < test_end_date)
+        else:
+            test_mask = (df[date_col] >= test_start_date)
+            
+        train_mask = df[date_col] < test_start_date
+        
+        splits.append((df[train_mask], df[test_mask]))
+        
+    return splits[::-1]  # Return in chronological order

+import numpy as np
+
+def calculate_metrics(actual: np.ndarray, predicted: np.ndarray) -> dict:
+    mae = float(np.mean(np.abs(actual - predicted)))
+    rmse = float(np.sqrt(np.mean((actual - predicted)**2)))
+    
+    total_actual = float(np.sum(actual))
+    
+    if total_actual == 0:
+        wape = None
+        missing_metric_reason = "Zero actual demand"
+    else:
+        wape = float(np.sum(np.abs(actual - predicted)) / total_actual)
+        missing_metric_reason = None
+        
+    return {
+        'mae': mae,
+        'rmse': rmse,
+        'wape': wape,
+        'missing_metric_reason': missing_metric_reason
+    }
+
+def seasonal_naive_forecast(history: np.ndarray, horizon: int, season_length: int = 7) -> np.ndarray:
+    """
+    Generate a seasonal naive forecast.
+    If there is enough history, use the same day from the previous season.
+    If not, use the last available value.
+    """
+    forecast = np.zeros(horizon)
+    for i in range(horizon):
+        # We need the value from `season_length` days ago.
+        # But we might be forecasting more than one season into the future.
+        # e.g., if forecasting day 8, we need day 1 of the forecast, which is day -6 of history.
+        
+        # Determine the historical index to pull from
+        # steps back from the *start* of the forecast window
+        steps_back = season_length - (i % season_length)
+        
+        if len(history) >= steps_back:
+            forecast[i] = history[-steps_back]
+        elif len(history) > 0:
+            forecast[i] = history[-1]
+        else:
+            forecast[i] = 0.0
+            
+    return forecast
