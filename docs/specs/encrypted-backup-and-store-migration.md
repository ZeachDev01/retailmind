# Encrypted backups, safe Database Restore, and Store Migration

Update 2026-10-31: [ADR-0023](../adr/0023-password-authorized-backup-restoration.md) supersedes the separate user-entered passphrase requirements for new backups and safety copies. Generated private keys provide encryption; the operator's current login password authorizes restoration. A separately saved recovery-key file supports server loss and migration. Older packages still require their original passphrase; other preservation and recovery requirements remain in force.

## Problem Statement

The Store owner needs recoverable backups and a dependable way to move the same Store between localhost and web hosting. A database-only SQL download leaves uploaded images behind, exposes captured records if stolen, and does not preserve the destination's privileged access when restored. Today, only the Super Administrator can restore, and full replacement also rolls back accounts, settings, and audit history.

The owner wants both Administrator roles to perform recovery without accidentally losing destination security controls, confusing historical staff identities, or operating two conflicting copies of the Store.

## Solution

Provide one encrypted, portable backup package containing a consistent database snapshot and the Store's required uploaded files. Both the Administrator and Super Administrator can create/download packages and perform Database Restore. Restore requires the current restoring user's destination login password and the separate passphrase used to create the selected package.

Support Store Migration in both directions between localhost and a separately prepared production hosting installation. Compatible application code and destination-specific configuration are installed first. Pause source operations and background writers for the final capture, transfer the package through download/upload, validate it, preserve destination security, retain a complete safety copy, and verify the destination before opening it for Store activity. Only one installation is active. This is replacement of Store state, not synchronization or merging of newer sales.

Keep destination Super Administrator and Recovery Account access, security settings, and security logs authoritative. Imported historical actions retain their correct actors. Reject ambiguous account conflicts before replacing anything. On the current hosting, Store operations may proceed after verification while forecasting remains unavailable; a compatible forecasting runtime is a later deployment choice.

## User Stories

1. As an Administrator, I want to create an encrypted backup, so that I can preserve the Store without depending on the technical owner.
2. As a Super Administrator, I want the same backup workflow, so that both authorized roles use one reliable capture process.
3. As an owner, I want the package to include Store data and uploaded Product/profile images, so that moving servers does not leave broken images behind.
4. As an owner, I want data and files captured consistently, so that the restored Store represents one coherent snapshot.
5. As an owner, I want stolen backup files to remain unreadable without their passphrase, so that possession alone does not expose Store records.
6. As an owner, I want a backup passphrase independent of login passwords, so that routine login-password changes do not invalidate backups.
7. As an owner, I want custody of the passphrase and a separate recovery copy outside both servers, so that server loss does not also destroy recovery access.
8. As an owner, I want clear guidance that losing all copies of a package's passphrase makes that package unusable, so that I do not expect a login-password reset to decrypt it.
9. As an authorized administrator, I want private, requester-bound downloads, so that another signed-in user cannot claim my temporary package.
10. As an authorized administrator, I want accurate backup history, so that capture completion is not mistaken for successful saving on my device.
11. As an Administrator, I want to perform Database Restore, so that routine recovery does not require Super Administrator presence when no security conflict exists.
12. As a Super Administrator, I want to retain restore and recovery authority, so that technical recovery remains possible.
13. As a Cashier or Inventory Manager, I must not gain backup or restore access, so that operational permissions do not expose complete Store copies.
14. As a restoring administrator, I want my current destination login password checked, so that possession of a backup is not enough to authorize replacement.
15. As a restoring administrator, I want to enter the selected backup's passphrase separately, so that authorization and decryption remain distinct.
16. As a restoring administrator, I want wrong passwords and passphrases rejected before replacement, so that mistakes leave the current Store intact.
17. As a restoring administrator, I want damaged, incomplete, incompatible, or unsafe packages rejected, so that an invalid package cannot partially replace the Store.
18. As an owner, I want a clear warning that an older snapshot replaces newer sales and other Store changes, so that I knowingly choose the recovery point.
19. As an owner, I want a verified destination safety copy saved before replacement, so that I can recover from an unsuccessful or mistaken restore.
20. As an owner, I want restore to abort if the safety copy cannot be saved, so that protection is never silently skipped.
21. As an owner, I want the Store kept closed after a partial failure, so that staff cannot sell against incomplete data or missing files.
22. As a recovery operator, I want a documented recovery procedure that works even if the users table is incomplete, so that failed replacement does not lock me out of recovery itself.
23. As a destination Super Administrator, I want my identity, credentials, role assignments, and security state preserved, so that an imported snapshot cannot replace my authority.
24. As an owner, I want the destination Recovery Account to remain usable under its existing sealed-recovery rules, so that migration does not undermine emergency access.
25. As a security owner, I want source privileged identities retained for attribution without automatically receiving destination privileged access, so that historical records survive without importing security authority.
26. As an auditor, I want every imported sale, approval, and historical action attributed to the correct person, so that colliding account IDs do not rewrite responsibility.
27. As a restoring administrator, I want conflicting account IDs, usernames, or emails reported before replacement, so that different people are never silently combined.
28. As a Super Administrator, I want a supported way to explicitly resolve reported identity conflicts before retrying, so that safe migration is possible without guessing or ad hoc database edits.
29. As a security owner, I want destination security settings and security logs preserved, so that restoring Store data cannot erase local security evidence or weaken access policy.
30. As an Administrator, I want Store sales, stock, operational staff, business settings, and history brought across, so that normal Store work continues from the selected snapshot.
31. As a security owner, I want imported restricted records kept under their existing visibility rules, so that Administrator restore access does not grant platform governance or restricted audit-screen access.
32. As an owner, I want to migrate localhost to hosting without exposing my local database publicly, so that a browser download/upload is sufficient to transfer the package.
33. As an owner, I want to migrate hosting back to localhost using the same workflow, so that changing the active host works in either direction.
34. As an owner, I want clear preparation instructions for compatible code, destination credentials, HTTPS, private storage, and resource limits, so that a backup is not mistaken for a complete server installer.
35. As an owner, I want destination configuration preserved, so that localhost URLs and credentials do not overwrite working hosting settings.
36. As an owner, I want source sales and background writers paused until cutover finishes, so that transactions cannot be stranded outside the transferred snapshot.
37. As an owner, I want verification before opening the destination, so that sign-in, stock, receipts, images, reports, and security controls are checked before selling resumes.
38. As an owner, I want a reminder to transfer fresh state before switching back after new sales, so that the inactive installation is never mistaken for an up-to-date fallback.
39. As an owner, I want the production hosting database isolated from the Hosted Demo, so that real records never replace or mingle with Demo Data.
40. As an owner, I want old forecasting jobs and source model pointers prevented from resuming on the destination, so that migration cannot silently use an invalid model or replay stale work.
41. As a Super Administrator, I want forecasting rebuilt and approved where the runtime supports it, so that forecasting resumes against the destination's actual data identity.
42. As an owner, I want verified sales and inventory to work while hosted forecasting is unavailable, so that the current hosting limitation does not block the rest of the Store.
43. As a restoring administrator, I want the new normal restore screen to accept encrypted packages only, so that plaintext SQL is not an alternate bypass.
44. As an owner, I want old SQL files retained privately until replacement encrypted backups have been restore-tested, so that introducing the new format does not destroy my existing recovery copies.
45. As a restoring administrator, I want clear progress, upload limits, rejection messages, and recovery instructions, so that I understand whether nothing changed, verification is pending, or recovery is required.
46. As a security owner, I want old sessions invalidated after restore and external restore evidence retained, so that rollback cannot revive stale access or erase who initiated replacement.
47. As an owner, I want migration and recovery proven using disposable installations, so that testing never destroys the live Store.

## Implementation Decisions

- **Reuse the existing workflow.** Extend DatabaseBackupService, DatabaseRestoreService, DatabaseSnapshotWriter, SqlBackupFormat, BackupCoordinator, RecoveryStore, StoreWriteGate, and the existing Administrator/Super Administrator screens and guarded entry points. Keep one capture/restore coordination path. Do not build a second exporter, job queue, synchronization engine, or general account-merging framework.
- **Narrow restore authorization.** Give both administrator roles explicit backup/restore authority without granting the Administrator PLATFORM_GOVERNANCE. Enforce authorization, current active account/session, active Workspace, and CSRF protection at every reachable endpoint, including legacy routes and downloads. Handle secondary role memberships consistently with the established authorization model; checking the primary role alone is insufficient.
- **Two distinct credentials.** Restore verifies the initiating administrator's current destination login password and decrypts using the package's original backup passphrase. Do not use login-password hashes as encryption keys or silently switch to login-password encryption. Never log or persist plaintext credentials, include them in filenames/URLs, or bundle a decryption key with the downloaded package. Passphrase changes for future packages do not change the secret needed for old packages.
- **Portable authenticated package.** Use a versioned format with authenticated encryption and an appropriate password-based key derivation mechanism from maintained, supported runtime libraries. Include compatibility metadata, the database snapshot, and required allowlisted uploads. Check available deployment libraries before choosing the format; do not invent cryptography. Ordinary backup output and the new ordinary restore input are encrypted packages only. Do not promise compatibility with the removed legacy encrypted format.
- **Safe package handling.** Validate decryption, complete contents, declared sizes, compatibility, database statements, references, security reconciliation, and allowed file destinations before replacement. Reject truncation, tampering, duplicate or missing members, path traversal, absolute paths, links, unexpected executable files, excessive expansion/resource use, and arbitrary SQL. Use the existing constrained SQL validation as appropriate; a checksum alone is not authentication. Reject unsafe input without overwriting destination files or Store records.
- **Coherent database and upload capture.** Cover the database and required uploaded Product/profile files under the same coordinated write pause. Define the allowlist from actual application storage. Exclude code, dependencies, environment credentials, server-specific paths, source recovery locks/state, and unrelated filesystem content. A package with only file references is not a complete migration package.
- **Private artifact lifecycle.** Keep temporary packages, decrypted staging, recovery material, and safety copies outside publicly served storage. Preserve requester binding and cleanup after delivery/expiry. Interrupted operations must not publish a partial package as complete. Backup history reports creation/delivery status truthfully and exposes only role-appropriate metadata.
- **Security boundary is an exception to full replacement.** The selected snapshot replaces Store operational records, operational accounts/roles, Store business settings, and historical records. Preserve destination privileged identities, full authentication and authorization state, Recovery Account sealing/activation data, platform security settings, security logs, and external restore evidence. Implement an explicit inventory of preserved tables/rows and dependent references; do not infer the boundary solely from table names, a password column, or primary role. Retain the fixed role/capability policy rather than importing arbitrary grants.
- **Source privileged identities and historical actors.** Retain source actors without granting source Super Administrator or Recovery Account authority. Remove imported privileged memberships; do not activate a source privileged-only account as a destination login. An existing legitimate operational role does not implicitly acquire privileged access. Preserve the correct actor for imported records and retained destination security history; never substitute a destination user merely because numeric IDs match.
- **Explicit identity conflict handling.** Preflight detects conflicting numeric identities, usernames, and emails and stops before replacement. Source and destination IDs do not prove two records are the same person. Provide a narrowly scoped, Super Administrator-controlled reconciliation/preparation procedure with explicit mappings where needed, validation of every dependent reference, and a retryable preflight. It must also work for a freshly provisioned destination whose seeded privileged IDs collide with source staff. Ordinary Administrator restore cannot resolve privileged conflicts implicitly. A supported workflow is required; instructing users to guess IDs or edit raw tables is not a complete implementation.
- **Preserved evidence remains distinguishable.** Keep existing destination security history and imported historical evidence attributable to their original identities; preserve provenance where both installations contribute records. Do not mix different actors or overwrite retained evidence through log-ID collisions. Existing Protected Audit Record visibility remains enforced. Administrator restore permission does not imply unrestricted inspection of protected records, even though an authorized holder of a decrypted complete backup can access its contents offline.
- **Safety copy covers the replacement scope.** Before destructive writes, create, verify, and retain a complete recoverable destination safety copy covering affected database records and uploads. Protect it with encryption/private storage and ensure the required decryption/recovery material survives a partially replaced database. Document which passphrase it requires. Do not overwrite the last good safety copy with partial state during a recovery retry. Abort before replacement if any part of safety capture or its verification fails.
- **Durable failure recovery.** Retain external locking, failure state, session invalidation, and append-only restore outcomes independently of the imported database. Track database/file replacement and verification so crashes cannot reopen an inconsistent Store. Recovery authenticates an authorized operator through protected pre-restore recovery state rather than trusting a partial users table; never save plaintext passwords. Provide and test a documented recovery path on localhost and the target hosting, including required console/SSH/operator access. Do not promise database DDL has transactional rollback or add an unauthenticated web bypass.
- **Transfer and activation.** Preparing a destination is separate from restoring. Use compatible application/schema versions and destination-specific database/mail/service configuration and private storage. Check required PHP extensions, limits, available memory/disk, upload allowance, and database compatibility before capture/import. Transfer via browser download/upload; no public localhost database or direct server-to-server database connection is required.
- **One active Store.** The final migration capture is taken after source sales and independent background writers are paused. Keep the source inactive through cutover. Destination verification precedes reopening for operations. Document how capture cancellation or migration abandonment returns the source to service only when the destination has not become active. The workflow is not automatic domain/DNS switching, automatic application deployment, or cross-server enforcement against an operator deliberately starting both copies.
- **Verify and invalidate sessions.** Validate database/file consistency, destination privileged/recovery access, operational sign-in, Product stock, Sale Receipts, reports, uploaded images, and job/security state before admitting ordinary Store activity. Invalidate old sessions even if restored account session-version fields match. Show a clear result and required next action rather than reporting completion before verification.
- **Forecasting portability.** Do not reactivate source model pointers or treat database-identity-bound model files as destination-ready. Prevent queued/running source work, leases, and attempts from replaying blindly after restore. Rebuild/reapprove models through existing forecasting services where supported. On current hosting, disable unsupported forecasting execution and state its unavailability clearly; do not silently serve old predictions as current destination forecasts.
- **Legacy handling.** Reject plaintext SQL in the new ordinary restore path. Keep old files private until a newly created encrypted package has been successfully restored and checked. Do not delete or relabel existing SQL/legacy encrypted artifacts or their required keys. A separate old-SQL recovery/conversion tool is not part of this change.
- **Interfaces and storage changes.** Update existing creation, download, history, restore, safety-copy, recovery-command, validation, and UI contracts coherently for the package and distinct credentials. Schema changes are permitted only where needed for explicit security/identity provenance or existing operation metadata; no speculative generic migration platform. Update existing tests/fixtures and operational instructions that currently assert plaintext export, SQL-only input, or Super Administrator-only restore.

## Testing Decisions

- The user confirmed the testing approach during specification synthesis: reuse the existing backup/restore workflow with disposable databases and uploaded files, plus checks through the actual Administrator screens. No tests use real Store records or destructive live hosting imports.
- Use the existing workflow integration boundary as the primary seam. Exercise real database snapshot, encrypted package creation/download, restore, files, coordinator, and recovery behavior together, asserting externally observable records, access, files, and outcomes rather than private helpers or implementation text.
- Extend the current real-MySQL backup workflow integration tests, constrained SQL format tests, authorization/route coverage, and injected interrupted-restore recovery scenarios. Retain focused format tests for malformed/security-sensitive inputs that are impractical to exhaust through a browser. Keep seams few; do not replace meaningful integration behavior with mocks for every service.
- Prove both roles can create/download/restore and other roles cannot. Exercise actual HTTP authorization, active Workspace/session checks, CSRF, requester-bound downloads, current destination password verification, wrong/old passwords, and separate correct/incorrect backup passphrases. Ensure restore access does not grant general platform governance or restricted audit-screen visibility.
- Test encrypted file theft properties by checking that captured sensitive plaintext is not exposed and that incorrect passphrases, altered packages, incomplete files, unsafe archive members, resource-limit violations, arbitrary SQL, and incompatible schemas fail before destination replacement. Test normal Unicode/binary data and valid upload references round-trip.
- Use separate source/destination fixtures with different credentials, colliding account IDs, distinct people with duplicate usernames/emails, secondary privileged role assignments, a sealed Recovery Account, destination security settings/logs, and imported historical actors. Prove conflicts reject safely, explicit reconciliation works on a fresh destination, destination security survives, and historical attribution is correct after successful retry.
- Test successful replacement removes post-snapshot operational changes while preserving destination security and source operational history as specified. Prove ordinary sessions are invalidated and restored session values cannot revive them.
- Test safety capture failure leaves the existing Store unchanged. Inject failures before replacement, during database replacement, during file replacement, and before final verification. Confirm incomplete state stays blocked, the last good complete safety copy survives, recovery works with a partial users table, and successful recovery restores both files and data without an unauthenticated bypass.
- Exercise both localhost-to-hosting and hosting-to-localhost deployment shapes using disposable installations. Confirm destination URLs/credentials remain local to that installation, source activity stays paused for cutover, checks precede destination opening, and returning after new transactions requires fresh state.
- Through both administrator screens, verify understandable warnings, distinct password labels, supported file type/size, actionable conflict/recovery messages, accessible form behavior, and accurate completion/history status. Existing navigation/status behavior must still work.
- Confirm stale jobs/model pointers do not run after migration, unsupported hosted forecasting stays unavailable, and supported destinations require model rebuild/approval before forecasting resumes. Verify production and Hosted Demo storage/database remain isolated.
- Before real migration, perform a supervised restore drill on a non-production target with the matching runtime. Demonstrate off-server passphrase recovery, complete verification, and recovery after failure. A browser-only smoke test is insufficient evidence of recoverability.

## Out of Scope

- Two simultaneously operating Store installations, continuous synchronization, merging divergent sales/stock, or multi-Store support.
- Selective restoration of individual sales, Products, or arbitrary database rows as an additional feature. Preserving security is a required restore boundary, not a general selective-restore interface.
- Bundling application code, deploying the application, provisioning hosting, purchasing a VPS, changing DNS/domains, or copying environment credentials automatically.
- Running Python forecasting on unsupported hosting, a new remote forecasting service, transparent model-artifact portability, or purchasing/configuring a compatible Python server.
- New automatic backup schedules, cloud storage integration, retention automation, or redesigning the separate local-Windows deployment work. Existing planned automation must be reconciled with the new format when implemented, not silently assume plaintext output remains supported.
- A general account-merging product, automatic identity guessing, importing source privileged authority, or granting Administrator platform governance.
- Accepting arbitrary SQL or legacy encrypted formats in the new restore screen, deleting old recovery files, or implementing legacy SQL conversion/recovery tooling in this change.
- Deploying to or performing destructive tests against the live Store or the Hosted Demo.

## Further Notes

This specification synthesizes the decisions confirmed on 2026-10-24. The later question about using only an admin password was a risk discussion, not a change of decision: both current destination login password and the separate original backup passphrase remain required.

The design intentionally revisits the plaintext/full-replacement policy in ADR-0004, the recovery authority boundary in ADR-0001, and relevant backup/recovery assumptions in the local-Windows deployment specification and issue #271. The encrypted portable workflow must preserve destination security rather than reuse today's unconditional full replacement. ADR-0017 records this target; existing operational instructions describe current behavior until implementation updates them.

The recorded Hostinger site is a Hosted Demo, not authorization to replace it with real Store data. A separate production site/database and deployment compatibility checks remain prerequisites. Hostinger's current documentation places Python support on VPS rather than Web/Cloud hosting; the user accepts hosted forecasting remaining unavailable for now. No server purchase or production migration is authorized by this issue.

Losing all copies of a package's passphrase makes the package unrecoverable. An encrypted package is not proof that its creator supplied trustworthy business data: anyone holding the passphrase and a compatible exporter may construct a valid package. Continue requiring trusted backups, authorized destination login, semantic validation, explicit identity/security preservation, and a recoverable safety copy.

Implementation must update the domain/context and recovery guidance alongside the changed behavior and reconcile related planned deployment work. Do not mark the feature complete with unresolved identity mappings, incomplete security preservation, database-only safety recovery, or an untested hosting recovery path.
