# Current inventory-manager and cashier workflows: barcode scanner trace

Scope: repository implementation, not a deployment test. This note follows the repo's existing `docs/research/` convention (`docs/research/password-alphanumeric-validation.md:1-7`). Paths and line numbers below are relative to the repository root. The role landing routes are Inventory Overview for `inventory_manager` and POS for `cashier` (`src/backend/app/Authorization/RoleWorkspaceRouter.php:7-15`); the sidebar links to their operational pages (`src/frontend/components/sidebar.php:163-170,203-243`).

## Inventory Manager: working sequence

1. Open Inventory Overview to see stock metrics, movements, low/out-of-stock items and a Stock Receiving link; navigate to Products & Stock, insights, counts, stock-issue reviews, reorder planning, suppliers, purchase orders, requests and forecasts from the sidebar (`src/frontend/components/inventory_management/inventory_overview.php:66-78,95-117,135-155,175-196`; `src/frontend/components/sidebar.php:163-170,203-225`). The role has `MUTATE_INVENTORY`; administrator and cashier do not have that base capability (`src/backend/app/Authorization/RoleCapabilityPolicy.php:35-56`).
2. In Products & Stock, Add Product has Basic → Barcode → Pricing → Planning → Review steps. At **Barcode**, type/USB-enter a code into the text field, click **Scan** to use the browser camera, click **Generate**, or leave it blank; case/package barcode is a separate optional input (`src/frontend/components/inventory_management/products.php:737-780,1549-1588`). Camera success only fills the barcode input and stops that camera; it does not create the product or change stock (`src/frontend/components/inventory_management/products.php:1560-1583`). Saving submits the form to the same PHP route, guarded by inventory-mutation capability and CSRF, and calls `ProductService::createProduct()` with zero initial stock (`src/frontend/components/inventory_management/products.php:31-34,48-50,88-110`). The service generates an internal code if blank, validates length and collisions (including SKU/case-code collisions), saves the selected/generated value as **both SKU and barcode**, and inserts inventory with the supplied zero quantity (`src/backend/app/Services/ProductService.php:90-102,128-166,540-564`). The UI Generate button constructs a candidate client-side; final collision validation occurs server-side (`src/frontend/components/inventory_management/products.php:1552-1559`; `src/backend/app/Services/ProductService.php:90-102`).
3. If the checked print-after-create option remains selected, saving redirects to printable labels; existing uncoded products can also have an internal barcode assigned before printing. The print route renders Code 128-B SVG for nonempty printable codes, skips empty codes and offers Generate Barcode and Print for a single uncoded product; printing invokes the browser print dialog (`src/frontend/components/inventory_management/products.php:122-128,803-808,141-148`; `src/frontend/components/inventory_management/print_barcodes.php:26-39,53-69,84-116`; `src/backend/includes/barcode.php:2-11,28-43`). **Creating/printing a barcode is not scanning stock in** (`src/frontend/components/inventory_management/products.php:108-110`; `src/frontend/components/report/stock_receiving.php:14-41`).
4. Replenish by selecting recommended products to create pending requests (or submitting a request, optionally from a forecast); an administrator approves requests, the manager can create a draft purchase order from approved requests, and administrator approval is required before marking the PO sent (`src/frontend/components/inventory_management/reorder_planner.php:19-22,44-89`; `src/frontend/components/inventory_management/replenishment_requests.php:13-42,73-75`; `src/frontend/components/invoice/purchase_orders.php:7-18`). Stock Receiving chooses an active product or a PO/request line, selects units/packages, enters quantities, damaged units, supplier and documents, and POSTs to `ReceivingService::receiveStock()`; its product control is a **select**, not a camera scanner (`src/frontend/components/report/stock_receiving.php:14-41,56-59,86-103,106-160,173-186`).
5. Other stock-control paths include CSV product import (blank SKU/barcode yields generated internal code), emergency adjustment with reason, count submission/approval, and manager-only approval/rejection/return of cashier stock issues; issue approval deducts stock, rejection does not (`src/frontend/components/inventory_management/csv_import.php:45-75`; `src/frontend/components/inventory_management/products.php:154-165,834-841`; `src/frontend/components/inventory_management/inventory_counts.php:41-70`; `src/frontend/components/inventory_management/stock_issues.php:16-24,29-62`). None of those cited form handlers is triggered merely by detecting a code (`src/frontend/components/inventory_management/products.php:1549-1589`; `src/frontend/components/report/stock_receiving.php:14-39`; `src/frontend/components/inventory_management/stock_issues.php:22-31`).

## Cashier: working sequence

1. Open Cashier Shift with opening cash, optionally record pay-in/pay-out, and close with counted cash for reconciliation (`src/frontend/components/cashier/shifts.php:19-37,61-74,94-109`; `src/backend/includes/operational_schema.php:96-121`). POS shows a missing-shift warning and disables checkout/hold if a cashier has no open shift; checkout service rechecks the shift inside the transaction (`src/frontend/components/cashier/pos.php:9-12,136-138,822-865`; `src/backend/app/Services/SalesWorkflowService.php:20-44,149-168`).
2. At POS **Scan an item**, a keyboard-wedge USB scanner can type into the focused **Barcode or SKU** input; a human can type the same code and press Enter or click Add item. Alternatively Use camera starts an in-page `Html5Qrcode` reader; decoding fills that **same input** and calls the same add-code function, with cooldown and duplicate-scan suppression (`src/frontend/components/cashier/pos.php:143-175,1098-1118,1193-1195,1263-1268`). The camera requires the loaded scanner library, a secure context/localhost, browser camera support and permission; failures tell the user to enter manually (`src/frontend/components/cashier/pos.php:377,1120-1163`).
3. The shared POS code lookup first checks its page-loaded top-120 active-products SKU/barcode map; a miss POSTs the code to `barcode.php` (`action=search`, default) which searches active products by exact barcode, SKU **or case barcode**. Thus a case barcode can resolve via the server fallback, but is not pre-indexed in the local map (`src/frontend/components/cashier/pos.php:54-92,390-396,667-711`; `src/frontend/components/barcodeScanner/apiScanner/barcode.php:33-35,55-70`). On match the POS adds one unit to its browser cart, constrains it by available stock, and offers quantity changes; quick-add cards are another non-scanner path (`src/frontend/components/cashier/pos.php:714-755,758-776,518-524`). The separate Find Product page searches by name/SKU/barcode through `products.php`; its lookup is not camera capture (`src/frontend/components/cashier/findProduct.php:25-46,70,130-151`; `src/frontend/components/barcodeScanner/apiScanner/products.php:30-60`).
4. Enter payment (cash/card/e-wallet), optional discount and required references/reason as appropriate, review confirmation, then POST the product IDs and quantities to POS. `SalesWorkflowService::checkout()` rechecks active products/stock and nonexpired batch allocation, requires the cashier's open shift, inserts sale/items, depletes batches/inventory and records negative sale stock movements; success redirects to Sales/transaction detail (`src/frontend/components/cashier/pos.php:29-50,911-983`; `src/backend/app/Services/SalesWorkflowService.php:20-53,103-145,149-168,365-431,448-496`). Scanning alone only builds the cart, **not a sale or inventory deduction** (`src/frontend/components/cashier/pos.php:714-755,911-983`; `src/backend/app/Services/SalesWorkflowService.php:20-44,365-391`). Held sales have an API and POS hold/resume UI; `persistHeldSales()` itself is empty, while the current cart is stored in sessionStorage (`src/frontend/components/cashier/pos.php:985-1045,1081-1095`).
5. For a stock issue, an open-shift cashier scans with a keyboard-wedge into a plain text input **or types a barcode**, then presses Enter to query `products.php?code=...`; they must select the returned product and enter issue type, quantity, explanation before submitting. Search by name/SKU/barcode is an alternative. Submission creates a pending report without changing inventory; an Inventory Manager reviews it (`src/frontend/components/cashier/stock_issues.php:20,47-58,111-174,291-345,348-375`; `src/frontend/components/inventory_management/stock_issues.php:16-44`). There is **no camera reader on this stock-issue page**: its cited markup/handler uses text input and GET lookup (`src/frontend/components/cashier/stock_issues.php:120-133,326-345`).

## Separate phone/tablet scanner, permissions and integration limits

- `components/barcodeScanner/index.html` is a standalone camera-scanning page with settings for server URL, six-character pairing code, `search`/`update_stock` and auto-send; settings/token persist in localStorage, while its displayed last-eight history is in-memory only (`src/frontend/components/barcodeScanner/index.html:71-106,163-180,237-254`). Start opens an explanatory permission modal, then starts a camera if the library, secure context and camera API are available; otherwise it reports a failure (`src/frontend/components/barcodeScanner/index.html:111-129,350-406,473-483`). On each decode, auto-send POSTs `barcode`, `action`, pairing code/token to the configured URL; with auto-send off it displays the code locally. Its iframe `postMessage` has no corresponding receiver in the traced POS handlers, whose own reader calls `addCodeFromInput()` (`src/frontend/components/barcodeScanner/index.html:268-301,334-347`; `src/frontend/components/cashier/pos.php:1098-1118,1193-1195`).
- Pairing API **implements** create (logged-in admin/manager/cashier + CSRF; 10-minute code and scanner URL), anonymous join (code → per-device token), owner-only status/poll, and scan logs on paired `search` requests (`src/frontend/components/barcodeScanner/apiScanner/pairing.php:36-104`; `src/backend/includes/pairing.php:11-46,50-66,89-119,131-156`; `src/frontend/components/barcodeScanner/apiScanner/barcode.php:68-89`). But the checked-in POS has no pairing-create/poll call; the phone page only joins a previously created code, and the standalone page has no cart-add call. Therefore the phone-to-laptop **automatic POS-cart handoff is not wired up by these UI paths** (`src/frontend/components/cashier/pos.php:436-440,667-727,1098-1118,1193-1195`; `src/frontend/components/barcodeScanner/index.html:205-225,268-301,334-347,448-465`; `src/frontend/components/barcodeScanner/apiScanner/pairing.php:55-102`). An additional USB/ADB handoff endpoint exists, but requires a valid owned pairing, CSRF, ADB and authorized Android device; it is not the ordinary keyboard-wedge input and is not called by the traced POS/phone UI (`src/frontend/components/barcodeScanner/apiScanner/usb_connect.php:17,64-101,104-137`; `src/frontend/components/cashier/pos.php:143-175,1193-1195`).
- Barcode API `search` accepts an authenticated session **or** a valid connected pairing token and returns product info (plus paired scan log), not cart state; `update_stock` instead requires `MUTATE_INVENTORY` and CSRF and uses `quantity` to set absolute inventory, writing an adjustment movement (`src/frontend/components/barcodeScanner/apiScanner/barcode.php:42-53,68-111`). The phone's Update Stock option sends neither `quantity` nor CSRF and supplies no quantity-entry control, so it is **not a functional manager stock-count workflow** as wired; a paired phone token by itself also supplies no logged-in mutation capability/session user ID (`src/frontend/components/barcodeScanner/index.html:93-102,268-286`; `src/frontend/components/barcodeScanner/apiScanner/barcode.php:92-109`; `src/backend/app/Authorization/RoleCapabilityPolicy.php:45-56`). The absolute-quantity API path updates `inventory` plus `stock_movements` directly; contrast the sale's batch depletion path (`src/frontend/components/barcodeScanner/apiScanner/barcode.php:100-109`; `src/backend/app/Services/SalesWorkflowService.php:365-391`).
- Distinguish product lookups: `barcode.php` searches *active* products by exact code but does **not** filter positive/sellable batch stock; `products.php` normally filters active products with positive on-hand and nonexpired sellable units (management `scope=all` is different). POS's local top-120 map also holds active products regardless of stock; final checkout enforces stock/batch rules (`src/frontend/components/barcodeScanner/apiScanner/barcode.php:55-65`; `src/frontend/components/barcodeScanner/apiScanner/products.php:11-28,30-60`; `src/frontend/components/cashier/pos.php:54-67,390-396`; `src/backend/app/Services/SalesWorkflowService.php:103-145,448-496`). A generated/scanned product barcode can be a non-ASCII string accepted at create time but fail Code 128-B printing (print renderer only accepts ASCII 32–126); the form/service and renderer have different constraints (`src/backend/app/Services/ProductService.php:90-102`; `src/backend/includes/barcode.php:7-12,30-36`; `src/frontend/components/inventory_management/print_barcodes.php:62-67`).

### Implemented vs documented/uncertain

First-party release notes describe Scan/Generate/labels and a server-side POS lookup, but the current POS also preloads a top-120 active-product map; descriptions of a laptop pairing screen or an automatic phone-driven checkout should not be inferred from those notes or the phone's UI copy (`backend/docs/release-notes/BARCODE_FEATURE_UPDATE.md:5-14`; `backend/docs/release-notes/OPERATIONAL_UPDATE_2026.md:5-5`; `src/frontend/components/cashier/pos.php:54-92,390-396,667-711`; `src/frontend/components/barcodeScanner/index.html:21-27,79-90,205-225`). This is a static trace; it does not establish camera availability, installed ADB, the live DB schema/data, or device/browser interoperability in a specific deployment (`src/frontend/components/cashier/pos.php:1134-1163`; `src/frontend/components/barcodeScanner/apiScanner/usb_connect.php:64-75`; `src/backend/includes/pairing.php:4-47`).
